🎯1. 概述与学习目标

FICL Chatbot 可在普通电脑上本地运行量化后的 GGUF 大语言模型，也可以使用服务器配置的 API 模型，并依据用户上传的文档回答问题，是一个典型的 RAG（检索增强生成）聊天机器人。选择本地模型时，问题和检索到的资料不会发送给第三方模型服务。

🧭 你可以学到什么

  • GGUF 量化模型是什么，以及如何在 CPU/GPU 上运行。
  • RAG 流程：嵌入、向量检索与上下文注入。
  • 提示词工程的实际作用，以及 grounded 与 fallback 模式的区别。
  • 使用 FastAPI + SSE（服务器发送事件）实现逐令牌流式输出。
  • 同时引用多个文件的多文档 RAG设计方法。
💡
为什么使用本地 LLM？
① 学习与作业资料不外传　② 无 API 调用费用　③ 可离线运行　④ 可以直接观察内部工作流程。

⚙️2. 安装与启动

📋 准备工作

  • Python 3.10+ — 从 python.org 安装，并勾选“Add Python to PATH”。
  • 模型来源 — 本地运行需要 GGUF 文件（测试可选约 1GB 的 Qwen2.5-1.5B）；API 模式需在后端配置模型和密钥。
  • 至少 8GB 内存 — 运行较大模型建议 16GB 以上。

🚀 五分钟安装

1

准备模型

本地模式：从 HuggingFace 下载 GGUF 文件并放入 models/。API 模式：按 README 在后端 api_models.json 中登记模型并填写 api_key。

2

运行启动脚本

Windows 双击 start.bat；Linux/macOS 运行 ./start.sh。首次启动会创建虚拟环境并安装依赖，约需 5～10 分钟。

3

打开浏览器

http://localhost:7861

在顶部下拉框中选择本地模型或后端已配置的 API 模型。

4

上传资料并提问

点击 📁，上传 PDF、DOCX、XLSX、TXT 或 MD 文件，然后输入问题。

⚡
GPU 加速（可选）
使用 NVIDIA GPU 时，生成速度通常可提升 5～10 倍。具体安装方式请参阅 README 的“GPU 加速”章节。

💬3. 基本用法

🖥 界面说明

区域作用
顶部语言下拉框选择“中文”或“한국어”，界面文字与之后生成的回答会使用所选语言；已发送的对话不会自动翻译。选择会保存在浏览器中。
顶部模型下拉框选择后端提供的本地或 API 模型；不可用的模型会禁用。选择 API 模型后可点击“测试 API 连接”，手动检查密钥与模型配置；测试可能产生少量 API 费用。
📁 上传文件支持 PDF、DOCX、XLSX、TXT、MD；单文件最多 20 MB，每次最多 10 个且总量不超过 50 MB。不同名文件会追加，同名文件会替换旧内容；索引自动持久化。
已上传文件目录原文件保存在后端 uploads/，页面会列出文件、大小和片段数；可逐个删除并同步移除索引。旧索引若无原文件会显示“原文件未保存”。
清空全部资料永久删除所有上传的原文件和向量索引，使 RAG 回到无资料状态。
聊天输入框按 Enter 发送，按 Shift+Enter 换行。
回答下方信息显示本次使用的模型，以及回答是“基于资料”还是“资料范围外”。
☁️
使用 API 模型
由服务器管理员在 Git 忽略的 api_models.json 中登记 API 地址、模型清单与实际密钥 api_key；后端直接读取该字段，不再通过环境变量查找密钥。前端只发送所选模型 ID，不会接收密钥。列表显示“可用”仅表示已配置密钥，不代表服务端已验证密钥；使用 API 模型时，问题和 RAG 检索结果会发送给该 API 服务。配置示例见 README。
🔐
局域网访问
默认仅允许本机访问。若将 HOST 改为 0.0.0.0 等对外地址，必须先设置至少 16 个字符的独立 APP_ACCESS_TOKEN；访问者在网页输入该令牌。请优先使用 HTTPS，避免令牌在不可信网络中明文传输。
# api_models.json：一个服务可以配置多个模型
[{"id":"example","name":"Example API","base_url":"https://api.example.com/v1","api_key":"YOUR_KEY","models":["example-small","example-large"]}]

🏷 两种回答模式

徽章含义出现条件
📚 基于资料 · 引用 N 项主要依据上传文件中的事实回答，并用“（资料 1）”“（资料 2）”标注来源。问题与上传资料高度相关，相似度 ≥ 0.55。
💭 资料范围外 · 通用知识改用模型自身的通用知识回答，并在开头说明超出上传资料范围。没有索引，或问题与资料相关性较低。

🧠4. RAG 工作原理

RAG（Retrieval-Augmented Generation）即“检索 + 生成”。LLM 只能依赖训练时学到的知识，直接询问私有 PDF 或表格内容容易产生幻觉。RAG 会先从上传资料中检索相关片段，再把片段和问题一起交给 LLM，从而提高准确性。

📥 资料上传流程

PDF/DOCX/XLSX → 提取文本 → 每 500 字分块 → 嵌入为 768 维向量 → 持久化到 rag_index/

🔎 问题处理流程

用户问题 → 问题向量化 → 余弦相似度 Top-K → 判断模式 → 组装提示词 → LLM 流式生成

📐 核心公式

归一化向量的点积等于余弦相似度。越接近 1 表示语义越相关，越接近 0 表示越不相关。

sim(q, d) = q_vec · d_vec        # 归一化向量
mode = "grounded"  if max(sim) ≥ 0.55
mode = "fallback"  otherwise

📚5. 多文档 RAG——核心特点

常见 RAG 会从所有文本块中选择全局 Top-K。如果某一个文件的相似度普遍较高，它可能独占检索结果。FICL Chatbot 改为分别从每个上传文件中选择 Top-K，让不同文档都有机会进入上下文，便于跨资料比较和综合。

🆚 方法比较

方法优点缺点
全局 Top-K简单、快速。一个文档可能独占结果，其他文档被忽略。
按文档 Top-K ✓公平引用多个文档，适合比较与综合。会消耗更多上下文令牌。

📎 示例：上传三个文件后提问

# 上传的资料
- lecture_notes.pdf       （课堂笔记）
- textbook_ch3.pdf        （教材第 3 章）
- lab_results.xlsx        （实验结果）

# 问题
“请分析实验结果与教材理论有哪些不同。”

# 发送给 LLM 的上下文（每个文件取 Top-3）
[资料 1 · textbook_ch3.pdf]
  ...理论说明...
[资料 2 · lab_results.xlsx]
  ...测量数据表...
[资料 3 · lecture_notes.pdf]
  ...补充说明...

LLM 可以分别引用三份资料，例如说明“资料 1 与资料 2 的数值存在……差异”，并指出资料之间互相矛盾的部分。

🎓6. 应用场景——如何用于课程与作业

📖 课程资料综合助手

上传多门课程的 PDF 笔记，复习时比较同一概念在不同课程中的讲法。

例：“概率分布在统计学和机器学习课程中分别如何解释？”

🔬 论文评审与摘要

同时上传多篇论文，按文档比较核心主张、方法和局限。

例：“分别总结三篇论文在评估方法上的区别。”

📊 实验数据分析

同时上传实验结果 Excel 和理论教材 PDF，分析测量值与理论的偏差。

例：“测量值与理论预测相差多少？”

📝 报告与作业助手

上传参考资料后，在写作过程中即时核对事实，降低幻觉风险。

例：“根据这份资料，2023 年的销售额是多少？”

👥 小组共享知识库

汇总组员的研究资料，让每个人都能检索其他成员收集的内容。

例：在局域网开放 7861 端口，供同一网络中的组员访问。

🧪 模型对比实验

向 Qwen2.5-1.5B、EXAONE 和 Qwen3-8B 提出相同问题，比较质量与速度。

例：“为什么小模型更快，但回答质量通常更低？”

🏢 校内制度问答机器人

上传院系规章、课程表和手册，为新生提供问答服务。

例：“毕业需要多少学分？”“休学申请流程是什么？”

💼 面试准备与角色扮演

上传简历和公司介绍，让模型生成模拟面试题。

例：“根据我的简历生成 10 个可能的面试问题。”
⚠️
使用注意事项
① LLM 可能出错，重要事实务必回到原文核实。② 受版权保护的资料不要超出教学和学习范围传播。③ 上传含个人信息的文件前应先匿名化。

📖9. 术语表

下面整理了本项目以及 RAG/LLM 领域中的核心概念，可在阅读代码和 README 时查阅。

🧠 A. LLM 基础
LLM Large Language Model
拥有数十亿到数千亿参数的大语言模型，通常先在大规模文本上预训练，再进行指令微调，例如 GPT、Claude、Qwen。
令牌 · 分词器
令牌是 LLM 处理文本的基本单位；分词器负责在字符串与令牌 ID 之间转换。不同语言的字符与令牌比例不同。
上下文窗口 n_ctx
模型一次能够“看到”的最大令牌数。Qwen3-8B 在本项目中使用 8192 个令牌，超出后较早内容可能被截断。
幻觉
模型以可信语气编造错误事实的现象，例如引用不存在的论文。RAG 是降低幻觉的常用方法。
提示词
发送给模型的完整输入，包括系统角色与规则、用户问题，以及 RAG 检索到的参考资料。
微调 vs RAG
微调会重新训练模型权重，成本较高；RAG 保持模型不变，只注入外部知识。动态事实适合 RAG，固定风格和行为更适合微调。
📦 B. 量化与 GGUF
GGUF
GGML Universal Format。llama.cpp 使用的单文件模型格式，可同时包含权重、分词器和元数据。
量化
把 float32 权重压缩为 4 位等低精度格式，显著降低内存需求并提升速度，但可能略微损失准确度。
Q4_K_M · Q5_K_M · Q8_0
表示量化位宽和方案。Q4_K_M 在体积与质量之间较均衡；Q5_K_M 更大、质量更高；Q8_0 接近原始质量。
n_gpu_layers
指定卸载到 GPU 的模型层数。-1 表示全部，0 表示只使用 CPU；显存不足时应减小数值。
bf16 · fp16 · fp32
不同的数值精度。fp32 精度最高且占用最大，fp16/bf16 使用 16 位；bf16 动态范围更宽，常用于现代 GPU。
🔍 C. RAG 核心概念
RAG · 检索增强生成
先检索与问题相关的资料片段，再连同问题一起交给 LLM 生成答案，是注入外部知识的实用方法。
分块 chunk_text()
把长文档切成较小片段。本项目每块 500 字、重叠 80 字；过大会降低检索精度，过小会损失上下文。
重叠（Overlap）
相邻文本块共同保留的字符数，可防止句子在边界处被切断，通常取块大小的 10%～20%。
Top-K 检索
只把相似度最高的 K 个文本块交给 LLM。K 通常取 3～5；过多会引入噪声，过少可能漏掉信息。
上下文注入
把检索片段写入系统提示词。本项目使用 [资料 N · 文件名]标注每个来源。
🎯 D. 嵌入与相似度
嵌入（Embedding）
把文本转换为高维数字向量，例如 768 维。语义相近的文本在向量空间中通常距离更近。
余弦相似度
两个向量夹角的余弦值，范围从 -1 到 1。对归一化向量可直接通过点积计算。
sim(q, d) = q_vec · d_vec
归一化 normalize_embeddings=True
将向量长度缩放为 1，使余弦相似度可以用快速点积计算。本项目在存储和查询时都会归一化。
E5 intfloat/multilingual-e5-base
本项目默认嵌入模型。查询需加 query: 前缀，文档需加 passage: 前缀，以匹配其训练方式。
BGE-M3 BAAI/bge-m3
可选升级模型，支持 Dense、Sparse 和 ColBERT，多语言、长文档与专业术语能力较强，但体积更大。
Dense vs Sparse
稠密向量主要用于语义匹配；稀疏向量大部分维度为零，更接近关键词匹配。混合检索会同时使用两者。
🔎 E. 检索算法
BM25
基于词频和逆文档频率的传统关键词检索算法，擅长匹配专有名词、数字和专业术语。
TF-IDF
BM25 的前身，降低常见词权重、提高稀有词权重。本项目当前代码未实现 TF-IDF/BM25 回退检索。
混合检索
对 BM25 关键词分数和嵌入语义分数进行加权组合，例如 final = 0.3·BM25 + 0.7·cosine。
重排序（Reranking）
先快速召回 Top-20，再用 Cross-Encoder 精排为 Top-3。质量更高，但速度更慢。
Cross-Encoder
同时输入查询和文档并直接判断相关度，通常比双塔嵌入更准确，但需要对每一对内容单独推理。
ColBERT
在令牌级别比较查询与文档，而不是把整篇文档压缩成单个向量，因此能保留更多细节。
⚙️ F. 模式与阈值
📚 grounded 模式
基于上传资料回答，并用“资料 1”“资料 2”等标记引用，尽量减少幻觉。
💭 fallback 模式
问题超出上传资料范围时，改用模型的通用知识回答，并明确提示资料范围外。
max(sim)
问题与所有文本块相似度中的最大值，用于判断资料是否包含足够相关的内容。
RAG_STRICT_SIM = 0.55
grounded 与 fallback 的切换阈值。调高更保守，调低则更容易采用资料回答。
RAG_MIN_SIM = 0.40
文本块进入上下文的最低相似度；低于此值的内容会被过滤以减少噪声。
k_per_doc
每份文档选取的 Top-K 数量，默认值为 3。增大可获得更多信息，但也会消耗更多令牌。
🌐 G. 服务器、流式传输与推理后端
FastAPI
现代 Python 异步 Web 框架，可为 /upload、/chat 等端点自动生成 OpenAPI 文档，是本项目的后端框架。
SSE · 服务器发送事件
基于 HTTP 的服务器到客户端单向流式传输。本项目用它逐步发送模型生成的令牌。
令牌流式输出
无需等待完整回答生成完毕，模型每生成一小段就立即发送，使用户获得类似打字的实时反馈。
llama-cpp-python
llama.cpp C++ 推理引擎的 Python 绑定，负责加载和运行 GGUF 模型。
vLLM
针对 GPU 吞吐量优化的 LLM 服务框架，适合生产和大规模部署；本教学项目使用的是 llama.cpp。
TensorRT-LLM
NVIDIA 的 LLM 推理加速引擎，可在特定 GPU 与模型组合上实现很高速度，但配置较复杂。
🧰 H. 其他常用概念
Temperature · top_p
控制生成随机性。temperature=0 更确定，较高值更有创造性；top_p=0.9 表示从累计概率最高的 90% 候选中采样。
Function Calling · Tool Use
允许 LLM 请求调用外部函数，例如查询天气、使用计算器，再把结果整合到回答中。
RLHF
基于人类反馈的强化学习。人类对回答进行偏好排序，模型再根据这些偏好进行训练。
MTEB 基准
大规模文本嵌入评测基准，用于比较 E5、BGE 等嵌入模型在不同任务上的表现。
Zero-shot · Few-shot
Zero-shot 不提供示例直接下达指令；Few-shot 先给出少量示例，适合要求严格输出格式的任务。
Chain-of-Thought（CoT）
通过引导模型进行分步推理来提高复杂任务的表现。Qwen3 的 /no_think 可关闭额外思考以节省令牌。
OpenAI SDK 兼容
许多本地服务器兼容 OpenAI Chat Completions API，因此可直接使用标准 openai Python 包访问。
上下文注入风险
上传文件可能藏有“忽略所有指令”等恶意提示词，从而诱导模型改变行为。应只上传可信资料。

🎯 1. 개요와 학습 목표 1. Overview & Learning Objectives

FICL Chatbot은 GGUF 양자화된 LLM을 일반 PC에서 로컬로 실행하거나 서버에 등록된 API 모델을 사용하고, 업로드한 문서를 참고해 답변하는 RAG(Retrieval-Augmented Generation) 챗봇입니다. 로컬 모델을 선택하면 질문과 검색된 자료가 외부 모델 서비스로 전송되지 않습니다.

🧭 이 챗봇으로 배울 수 있는 것

  • GGUF 양자화 모델이 무엇인지, 어떻게 CPU/GPU에서 동작하는지
  • RAG의 원리 — 임베딩, 벡터 검색, 컨텍스트 주입
  • 프롬프트 엔지니어링의 실제 효과 (grounded vs fallback 모드 비교)
  • FastAPI + SSE(Server-Sent Events) 기반 토큰 스트리밍
  • 여러 문서를 동시에 참조하는 다중문서 RAG 설계 방식

FICL Chatbot runs a quantized GGUF LLM locally on your PC or uses an API model configured on the server, with uploaded documents as reference material — a RAG (Retrieval-Augmented Generation) chatbot. When you choose a local model, your question and retrieved document snippets stay off third-party model services.

🧭 What you can learn

  • What GGUF quantized models are and how they run on CPU/GPU
  • The RAG pipeline — embeddings, vector search, context injection
  • Real impact of prompt engineering (grounded vs fallback mode)
  • Token-level streaming via FastAPI + SSE (Server-Sent Events)
  • How multi-document RAG references several files simultaneously
💡
왜 로컬 LLM을 쓰나요? Why a local LLM?
① 과제 자료가 외부로 유출되지 않음 ② API 비용 無 ③ 오프라인에서도 동작 ④ 내부 작동 원리를 직접 확인 가능 ① Your assignments stay private ② No API cost ③ Works offline ④ You can inspect every internal step.

🧠 4. RAG 작동 원리 4. How RAG Works

RAG (Retrieval-Augmented Generation) = "검색" + "생성". LLM은 학습 당시에 본 지식만 압니다. 그래서 여러분의 PDF·DOCX처럼 모델이 모르는 내용을 질문하면 환각(hallucination)을 일으키기 쉽습니다. RAG는 질문과 관련된 부분을 자료에서 미리 찾아 LLM에 함께 넣어줘서 이 문제를 해결합니다.

RAG (Retrieval-Augmented Generation) = "retrieve" + "generate". An LLM only knows what it saw during training, so when you ask about your own PDFs or Excel sheets, it tends to hallucinate. RAG fixes this by searching your documents first and injecting the relevant snippets into the LLM prompt.

📐 핵심 수식

📐 Core Math

정규화된 벡터의 내적 = 코사인 유사도. 임베딩이 서로 유사하면 1에 가깝고, 전혀 관련 없으면 0에 가깝습니다.

Dot product of normalized vectors = cosine similarity. Close to 1 means highly related, close to 0 means unrelated.

sim(q, d) = q_vec · d_vec        # 정규화된 벡터normalized vectors
mode = "grounded"  if max(sim) ≥ 0.55
mode = "fallback"  otherwise

📚 5. 다중문서 RAG — 핵심 차별점 5. Multi-Document RAG — The Key Feature

일반적인 RAG는 모든 청크 중에서 "전역 top-K"를 뽑습니다. 문제는 특정 파일 하나가 다른 파일보다 유사도가 높으면 결과를 독식해버린다는 점. FICL Chatbot은 각 업로드 파일마다 자체 top-K를 뽑아서, 서로 다른 문서를 공평하게 참조합니다.

Vanilla RAG picks a global top-K across all chunks — one dominant file can starve the others. FICL Chatbot selects a per-file top-K, so every uploaded document gets its fair share of the context window.

🆚 비교

🆚 Comparison

방식장점단점 MethodProsCons
전역 top-K 단순, 빠름 한 문서가 결과 독식 → 다른 문서 참조 불가 Global top-K Simple, fast One doc can hog results → others ignored
문서별 top-K ✓ 여러 문서를 공평하게 참조. 자료 간 비교·종합 가능 약간 더 많은 토큰 사용 Per-doc top-K ✓ Fair reference across docs; enables cross-doc comparison Slightly more tokens

📎 예시: 3개 파일 업로드 상태에서 질문

📎 Example: Query with 3 files uploaded

# 업로드한 자료# Uploaded files
- lecture_notes.pdf       (강의 노트)(lecture notes)
- textbook_ch3.pdf        (교재 3장)(textbook ch3)
- lab_results.xlsx        (실험 결과)(lab results)

# 질문# Query
"실험 결과가 교재 이론과 어떻게 다른지 분석해줘Compare the lab results against the textbook theory"

# LLM이 받는 컨텍스트 (각 파일에서 top-3)# Context delivered to the LLM (top-3 from each)
[자료 1 · textbook_ch3.pdf]
  ...이론 설명theoretical description...
[자료 2 · lab_results.xlsx]
  ...측정값 표measurement table...
[자료 3 · lecture_notes.pdf]
  ...보완 설명supplementary notes...

LLM은 세 자료를 각각 참조하면서 "(자료 1)과 (자료 2)의 수치는 ~ 다르다" 식으로 명확한 인용을 넣어 답변합니다. 자료 끼리 상충하는 부분도 짚어줍니다.

The LLM cites each source — e.g., "The values in (자료 1) differ from (자료 2) by ..." — and flags any contradictions between them.

🎓 6. 활용 방안 — 수업·과제에서 어떻게 쓰나? 6. Use Cases — How to Apply in Class

📖 강의 자료 종합 비서Lecture Study Buddy

여러 강의의 PDF 노트를 모두 업로드. 시험 준비 시 특정 개념이 서로 다른 강의에서 어떻게 다뤄졌는지 비교 질문.

Upload PDF notes from several lectures. At exam time, ask how one concept appears across different lectures.

예: "확률분포가 통계 강의와 기계학습 강의에서 각각 어떻게 설명됐어?"
Ex: "How was probability distribution explained in both statistics and ML lectures?"

🔬 논문 리뷰 요약Paper Review Summarizer

여러 관련 논문의 PDF를 함께 업로드. 핵심 주장·방법론·한계점을 자료별로 비교 추출.

Upload several related papers and extract claims / methods / limitations per paper.

예: "세 논문이 제시한 평가 방법의 차이점을 각각 정리해줘"
Ex: "Summarize how the three papers differ in evaluation methodology."

📊 실험 데이터 분석Experiment Data Analysis

실험 결과 Excel + 이론 교재 PDF를 함께 업로드. 수치와 이론의 괴리 분석.

Upload experimental Excel + theory PDF to spot deviations between measurement and theory.

예: "측정값이 이론 예측과 얼마나 차이 나는지 분석"
Ex: "By how much do measured values deviate from predicted?"

📝 보고서·과제 작성 도우미Report Writing Assistant

참고 자료를 업로드해두면 사실관계를 즉시 확인하며 글을 쓸 수 있음. 환각 방지.

Upload references and verify facts on the fly while writing — avoid hallucinations.

예: "이 자료에 따르면 2023년 매출 수치는?"
Ex: "What was the 2023 revenue figure per this document?"

📖 9. 용어 사전 (Glossary) 9. Glossary

이 챗봇과 RAG·LLM 전반에 등장하는 핵심 용어 정리. 코드와 README를 읽을 때 참고하세요.

Reference for all key terms used in this chatbot and the broader RAG/LLM ecosystem. Keep this handy while reading the code and README.

🧠 A. LLM 기초 🧠 A. LLM Fundamentals
LLM Large Language Model
수십억~수천억 개의 파라미터를 가진 대규모 언어 모델. 인터넷 텍스트로 사전학습 → 명령 지시(Instruction) 추가 학습. GPT-4, Claude, Qwen 등. Massive language models with billions of parameters, pretrained on web text and instruction-tuned. GPT-4, Claude, Qwen, etc.
토큰Token · 토크나이저Tokenizer
LLM이 다루는 최소 단위. 영어는 보통 1단어 ≈ 1토큰, 한국어는 1글자 ≈ 1~2토큰. "안녕하세요" ≈ 4토큰. 토크나이저가 문자열 ↔ 토큰 ID 변환. The atomic unit an LLM processes. English ≈ 1 word/token; Korean ≈ 1~2 tokens per char. "Hello" ≈ 1 token. Tokenizer converts text ↔ token IDs.
컨텍스트 길이Context Window n_ctx
모델이 한 번에 "기억"할 수 있는 토큰 수. Qwen3-8B는 8192토큰(≈ A4 10장). 초과하면 앞부분이 잘림. Max tokens the model can "see" at once. Qwen3-8B = 8192 tokens (~10 pages). Overflow truncates older content.
환각Hallucination
LLM이 사실이 아닌 걸 그럴듯하게 지어내는 현상. "존재하지 않는 논문 인용" 같은 것. RAG는 이걸 줄이기 위한 대표적 방법. When an LLM confidently fabricates plausible-sounding falsehoods (e.g., fake citations). RAG is a primary mitigation.
프롬프트Prompt
LLM에게 주는 입력 전체. 시스템 프롬프트(역할·규칙) + 사용자 질문 + (RAG일 땐) 참고 자료. The full input to the LLM: system prompt (role/rules) + user query + (if RAG) retrieved context.
파인튜닝Fine-tuning vs RAG
파인튜닝은 모델 가중치를 다시 학습 (비용·시간 큼). RAG는 모델 그대로 두고 외부 지식만 주입 (빠르고 저렴). 변하는 지식 = RAG, 고정된 스타일 = 파인튜닝. Fine-tuning retrains model weights (costly). RAG keeps the model fixed and injects external knowledge (fast, cheap). Dynamic facts → RAG; fixed style → fine-tune.
📦 B. 양자화 · GGUF 모델 📦 B. Quantization & GGUF
GGUF
GGML Universal Format. llama.cpp에서 쓰는 양자화 LLM 파일 포맷. 한 파일에 가중치·토크나이저·메타데이터 모두 포함. GGML Universal Format — a single-file format from llama.cpp bundling weights, tokenizer, and metadata.
양자화Quantization
가중치를 32비트(float32) → 4비트로 압축해 메모리 1/8, 속도 ↑. 정확도 약간 손실. 큰 모델을 일반 PC에서 돌리는 핵심 기술. Compress weights from float32 → 4-bit, cutting memory 8× and boosting speed with slight accuracy loss. Essential for running large models on consumer PCs.
Q4_K_M · Q5_K_M · Q8_0
양자화 비트 수와 방식. Q4_K_M(4bit, medium quality) = 균형. Q5_K_M = 품질 ↑ 크기 ↑. Q8_0 = 거의 원본 품질. Quantization bit-width + scheme. Q4_K_M (4-bit, medium) is balanced. Q5_K_M = higher quality, bigger. Q8_0 ≈ near-original.
n_gpu_layers
모델 레이어 중 몇 개를 GPU에 올릴지. -1=전체, 0=CPU만. VRAM 부족 시 숫자 줄임. 24GB GPU면 보통 -1. How many layers to offload to GPU. -1=all, 0=CPU only. Lower if VRAM is tight. 24GB GPUs usually run -1.
bf16 · fp16 · fp32
숫자 정밀도. fp32(32비트) 원본 → fp16/bf16(16비트)로 반 토막 → 4비트 양자화로 추가 축소. bf16은 범위 넓고 품질 안정 → 최신 GPU 기본값. Numeric precision. fp32 original → fp16/bf16 (half) → 4-bit quantization (further). bf16 has wider range → default on modern GPUs.
🔍 C. RAG 핵심 개념 🔍 C. Core RAG Concepts
RAG · 검색 증강 생성
Retrieval-Augmented Generation. 질문과 관련된 자료를 먼저 "검색"해 LLM에 함께 넣어 "생성". 외부 지식을 모델에 주입하는 가장 실용적 방법. Retrieval-Augmented Generation. Retrieve relevant chunks first, then feed them to the LLM. The most practical way to inject external knowledge.
청킹Chunking chunk_text()
긴 문서를 작은 조각(청크)으로 자르는 작업. 이 챗봇은 500자/청크, 80자 overlap. 청크가 너무 크면 검색 정밀도 ↓, 너무 작으면 맥락 ↓. Split long docs into small pieces. Here: 500 chars/chunk with 80-char overlap. Too big = poor retrieval; too small = loss of context.
오버랩Overlap
인접 청크 간 겹치는 글자 수. 문장이 청크 경계에서 잘려 의미 손실되는 걸 방지. 보통 청크 크기의 10~20%. Characters shared between adjacent chunks — prevents sentences from being severed at boundaries. Typically 10–20% of chunk size.
Top-K 검색retrieval
유사도 상위 K개 청크만 LLM에 전달. K=3~5가 일반적. 많이 넣으면 노이즈, 적게 넣으면 정보 부족. Pass only the top-K most-similar chunks to the LLM. K=3–5 is typical. Too many = noise; too few = missing info.
컨텍스트 주입Context Injection
검색된 청크를 시스템 프롬프트 안에 "[참고 자료]..." 형태로 넣는 과정. 이 챗봇은 [자료 N · 파일명]으로 라벨링. Embedding retrieved chunks inside the system prompt as "[참고 자료]...". This chatbot labels each as [자료 N · filename].
🎯 D. 임베딩과 유사도 🎯 D. Embeddings & Similarity
임베딩Embedding
텍스트를 고차원 숫자 벡터(예: 768차원)로 변환한 것. 의미가 비슷하면 벡터도 가깝다. "강아지" ≈ "개", "강아지" ≠ "자동차". Converting text into a high-dim vector (e.g., 768-D). Similar meanings → nearby vectors. "dog" ≈ "puppy", "dog" ≠ "car".
코사인 유사도Cosine Similarity
두 벡터가 이루는 각도의 코사인. 1(동일) ~ 0(무관) ~ -1(반대). 정규화된 벡터면 단순 내적(dot product)으로 계산 가능. Cosine of the angle between two vectors. 1 (same) → 0 (unrelated) → -1 (opposite). For normalized vectors, equals a simple dot product.
sim(q, d) = q_vec · d_vec
정규화Normalization normalize_embeddings=True
벡터 길이를 1로 만듦. 코사인 유사도 계산을 내적만으로 빠르게 처리 가능. 이 챗봇은 저장·검색 때 모두 정규화. Scale vectors to length 1 so cosine similarity reduces to a dot product. This chatbot normalizes on both store and query.
E5 intfloat/multilingual-e5-base
이 챗봇의 기본 임베딩 모델(약 280MB). 쿼리에 query:, 문서에 passage: 프리픽스 필수 (학습 때 그렇게 썼기 때문). Default embedder (~280MB). Needs query: prefix for queries and passage: for documents (as trained).
BGE-M3 BAAI/bge-m3
업그레이드 후보 임베더(약 2.2GB). Dense·Sparse·ColBERT 다중 벡터 지원. 긴 문서(8K 토큰), 전문용어에 강함. E5보다 10~20% 정확. Upgrade candidate (~2.2GB). Supports dense + sparse + ColBERT. Handles 8K-token docs; 10–20% stronger than E5 on technical content.
Dense vs Sparse (조밀 vs 희소 벡터)
Dense = 모든 차원이 숫자(768차원 전부 사용 · 의미 매칭). Sparse = 대부분 0 (어휘 매칭 · BM25 계열). 하이브리드는 둘 다 사용. Dense = all dims filled (768-D, semantic match). Sparse = mostly zero (lexical match, BM25-like). Hybrid uses both.
🔎 E. 검색 알고리즘 🔎 E. Retrieval Algorithms
BM25
임베딩 없이 쓰는 전통 키워드 검색 알고리즘. TF(단어 빈도) × IDF(희귀도) 기반. 고유명사·숫자·전문용어 매칭에 강함. Classic keyword-only retrieval. Combines TF (term frequency) × IDF (rarity). Strong for proper nouns, numbers, and jargon.
TF-IDF
BM25의 전신. 자주 나오는 흔한 단어는 가중치 ↓, 희귀 단어는 ↑. 챗봇 코드에서 임베더 없을 때 폴백 검색에 사용. BM25's predecessor. Common words get lower weight, rare words higher. Used as fallback when no embedder is available.
하이브리드 검색Hybrid Search
BM25(키워드) + 임베딩(의미) 점수 가중 합산. 실무 검색 시스템은 거의 모두 하이브리드. 예: final = 0.3·BM25 + 0.7·cosine Weighted blend of BM25 (keyword) + embedding (semantic). Nearly all production retrieval is hybrid. Ex: final = 0.3·BM25 + 0.7·cosine.
재순위Reranking
1차로 top-20을 빠르게 뽑고, Cross-Encoder로 더 정밀하게 top-3 재정렬. 품질 ↑ 하지만 느림. 중요도 높은 자료 다룰 때 효과적. Fetch top-20 fast, then re-rank to top-3 with a cross-encoder for precision. Higher quality but slower. Worth it for high-stakes retrieval.
Cross-Encoder
쿼리와 문서를 함께 입력받아 "이 둘이 얼마나 관련 있나?" 점수 산출. 임베딩(bi-encoder)보다 정확하지만 매번 LLM 추론 필요 → 느림. Jointly scores a (query, doc) pair for relevance. More accurate than embeddings (bi-encoder) but requires inference per pair → slow.
ColBERT
문서 단위 벡터가 아니라 토큰 단위로 비교해 디테일 보존. BGE-M3가 지원하는 다중 벡터 방식 중 하나. Compares at the token level (not whole-doc), preserving detail. One of the multi-vector modes supported by BGE-M3.
⚙️ F. 모드 판정과 임계값 ⚙️ F. Mode Decision & Thresholds
📚 grounded 모드
"자료 기반" 모드. 업로드 자료 안의 사실만 사용. 답변에 (자료 1), (자료 2) 인용 표기. 환각 가능성 ↓. "Grounded" mode — answer only from uploaded facts, citing (자료 1), (자료 2). Minimizes hallucination.
💭 fallback 모드
"자료 범위 밖" 모드. LLM이 학습해둔 일반 지식으로 답변. 서두에 "(업로드 자료 범위 밖 · 일반 지식 기반)" 표시. "Out-of-scope" mode — answer from the LLM's general knowledge, prefixed "(out of uploaded scope · general knowledge)".
max(sim)
질문과 모든 청크의 유사도 중 최댓값. 자료 안에 질문과 얼마나 관련 깊은 내용이 있는지 측정. 모드 판정 기준. Maximum similarity between the query and any chunk. Measures how closely the docs match the question. Used for mode decision.
RAG_STRICT_SIM = 0.55
grounded/fallback 전환 임계값. max(sim) ≥ 0.55면 grounded. 올리면 보수적, 내리면 적극적. Threshold for grounded vs fallback. max(sim) ≥ 0.55 → grounded. Higher = conservative, lower = aggressive.
RAG_MIN_SIM = 0.40
청크 포함 최소 임계값. 이 값보다 유사도 낮은 청크는 아예 LLM에 전달 안 함 (노이즈 제거). Minimum similarity to include a chunk at all. Chunks below this are dropped before reaching the LLM (noise filter).
k_per_doc
문서별로 뽑을 top-k 청크 수. 기본 3. 늘리면 문서별 정보 많아지지만 토큰 소비 ↑. Top-K chunks to pick per document. Default 3. Higher = more info per doc, but more tokens consumed.
🌐 G. 서버 · 스트리밍 · 추론 백엔드 🌐 G. Server, Streaming & Backends
FastAPI
Python 비동기 웹 프레임워크. /upload, /chat 같은 엔드포인트를 자동으로 OpenAPI 스펙화. 이 챗봇의 백엔드. Modern async Python web framework. Auto-generates OpenAPI docs for endpoints like /upload, /chat. This chatbot's backend.
SSE · 서버 전송 이벤트
Server-Sent Events. HTTP 위에서 서버 → 클라이언트 단방향 스트리밍. ChatGPT 토큰별 출력도 SSE. WebSocket보다 가볍고 자동 재연결. Server-Sent Events — one-way streaming over HTTP. ChatGPT token streaming uses SSE. Lighter than WebSocket, with auto-reconnect.
토큰 스트리밍Token Streaming
LLM 응답을 완성 전에 1토큰씩 바로 보내서 사용자가 "타이핑처럼 글이 흘러나오는" 체감 지연 ↓. Push each generated token immediately so the user sees a "typewriter" effect, drastically reducing perceived latency.
llama-cpp-python
llama.cpp(C++ 추론 엔진)의 Python 바인딩. GGUF 모델 로딩 + 추론 담당. 이 챗봇의 LLM 백엔드. Python bindings for llama.cpp (C++ inference engine). Loads and runs GGUF models — this chatbot's LLM backend.
vLLM
GPU에 최적화된 고성능 LLM 서버. PagedAttention으로 처리량 ↑↑. 상용/대규모 서빙용. 교육용 FICL은 llama.cpp 쓰지만 AIEduChatApp은 vLLM 사용 가능. High-throughput GPU-optimized LLM server (PagedAttention). For production/scale serving. FICL uses llama.cpp but AIEduChatApp also supports vLLM.
TensorRT-LLM
NVIDIA의 전용 LLM 추론 가속 엔진. 특정 GPU + 특정 모델에서 최고 속도. 설정 복잡. NVIDIA's proprietary LLM inference engine. Peak speed on specific GPU + model combos. Complex to set up.
🧰 H. 알아두면 좋은 개념 🧰 H. Nice-to-Know Concepts
Temperature · top_p
LLM 샘플링 랜덤성 조절. temperature=0.0 결정적(동일 질문 → 동일 답), 1.0+는 창의적. top_p=0.9는 "확률 상위 90% 안에서 샘플링". Controls randomness. temperature=0.0 = deterministic, 1.0+ = creative. top_p=0.9 samples from the top 90% probability mass.
Function Calling · Tool Use
LLM이 외부 함수를 호출할 수 있게 하는 기능. "오늘 서울 날씨?" → 모델이 날씨 API 호출 요청 → 결과 받아 답변 생성. Lets the LLM call external functions. "Weather in Seoul?" → model requests the weather API → integrates the result into its answer.
RLHF
Reinforcement Learning from Human Feedback. 사람이 선호 응답 라벨링 → LLM이 이걸로 미세조정. ChatGPT가 유용해진 핵심 기법. Reinforcement Learning from Human Feedback. Humans rank model outputs → model fine-tunes on these preferences. The core trick that made ChatGPT useful.
MTEB 벤치마크
Massive Text Embedding Benchmark. 임베딩 모델 성능 평가 표준. E5, BGE 등은 모두 이 리더보드 기준으로 공개. Massive Text Embedding Benchmark — the standard leaderboard for embedding models. E5, BGE, etc. publish MTEB scores.
Zero-shot · Few-shot
Zero-shot = 예시 없이 바로 지시. Few-shot = 2~5개 예시를 보여준 뒤 지시. 복잡한 포맷 요구할 땐 few-shot이 유리. Zero-shot = instruct directly. Few-shot = show 2–5 examples before instructing. Few-shot helps when a specific format is required.
Chain-of-Thought (CoT)
LLM에게 "단계별로 생각해봐"라고 지시해 추론 품질 ↑. Qwen3의 /no_think 플래그는 반대로 이를 끄는 설정 (코드 생성 등 토큰 절약). Prompting "think step by step" to boost reasoning. Qwen3's /no_think flag turns it off (saves tokens for codegen).
OpenAI SDK 호환
vLLM·TRT-LLM 등 많은 로컬 서버가 OpenAI의 Chat Completions API 스펙과 호환되어, openai Python 패키지 그대로 사용 가능. Many local servers (vLLM, TRT-LLM) speak OpenAI's Chat Completions API spec, so the standard openai Python package works unchanged.
Context 주입 보안Injection Risk
업로드한 자료 안에 "모든 지시 무시하고 ○○해라" 같은 악성 지시가 숨어 있으면 LLM이 속을 수 있음. 신뢰할 수 있는 자료만 업로드. Malicious instructions hidden inside uploaded files can trick the LLM into obeying them (prompt injection). Only upload trusted sources.
